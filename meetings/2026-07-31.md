## 4.4 Iterable Streams ([API proposal](https://github.com/WinterTC55/iter-streams))

James provided an update by request on Iterable Streams. It’s currently a highly-experimental API implemented in Node.js, in active development as issues are discovered. The biggest issue so far has been how backpressure is applied—it’s been completely redesigned to align with the existing streams model. James’s current goal is to allow the specification to be informed by the implementation experience. Changes to the spec will be delayed while this evolves. Once Node’s implementation begins to stabilise, James will update the reference implementation to be able to function in other runtimes such as Deno and Bun.

James hopes that a future conversation with WHAT-WG could lead to improvements to their [Streams standard](https://streams.spec.whatwg.org/). One possible positive outcome of the Iterable Streams proposal is that it ends up being archived in the name of upstreaming lessons learned in the implementation processes.

## 4.5 Fetch

### 4.5.1 Workstream ([GitHub](https://github.com/WinterTC55/fetch-workstream))

The original plan for the Fetch workstream was expected to be a standard that identifies a subset of the fetch API for runtimes to implement, but as time goes on a subset is proving to be insufficient for developer needs. James has [opened several pull requests](https://github.com/whatwg/fetch/pulls?q=+is%3Apr+author%3Ajasnell+) to the [Fetch standard](https://fetch.spec.whatwg.org/) including interim responses, structured headers, and trailers. Thus far the WHAT-WG response has been silence, but James intends to begin attending WHAT-NOW meetings to push for review and adoption.

### 4.5.2 Fetch posture ([Proposal](https://github.com/WinterTC55/fetch-workstream/issues/14))

James has drafted a proposal to potentially modify the source Fetch standard to provide consistent specification for non-browser contexts without making any changes to browser contexts. This has the benefit of avoiding a messy fork while also acknowledging priority number one for WHAT-WG, which is having to develop anything for non-browser runtimes. Additional tests would need to be submitted to [WPT](https://github.com/web-platform-tests/wpt), but those tests would not impact browsers.

One open question as brought up by Owen Buckley is whether non-browser runtimes would be expected to warn when user code appears to be expecting a browser context (and browser security).

James has brought this up in a WHAT-WG Matrix channel, to rather mute response. One person expressed support, no one has expressed explicit opposition.
